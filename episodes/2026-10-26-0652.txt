Australian focus first.

CYFIRMA, a threat intelligence firm, reports a suspected North Korean campaign probing PHP servers for the PHP to Shell flaws from twenty-one compromised machines. It says the operators have a filtered list of two hundred and sixteen unpatched or only partly mitigated hosts across a dozen countries and regions, including Australia, the United States, Japan, South Korea and Singapore, in government, finance, logistics, aviation, manufacturing and online payments. The scanning is deliberately slow, and nodes are dropped at the first sign of blocking, so simple threshold alerts are unlikely to catch it. CYFIRMA links it to the Lazarus Group ecosystem with moderate confidence, and this rests on that one vendor's reporting. The practical point for Australian organisations is the same one the Australian Cyber Security Centre made in its critical alert last Wednesday: patch PHP. But with a confirmed intrusion now on the record, if a server sat exposed and unpatched last week, checking it for signs of compromise matters as much as patching it.

Global threats.

The confirmed case comes from Palo Alto Networks' Unit 42. Attackers exploited the PHP to Shell flaws against a government entity in Europe, and within two hours they had reached password hashes and multi-factor authentication secrets. They then built a relay tunnel into Active Directory using NT LAN Manager, the older Windows authentication protocol, and tried to escalate to Domain Admin. The victim has not been named. What stands out is how the work was done. Each batch of commands was wrapped in labelled section headers, the kind of tidy, machine-readable output an AI model needs to read its own results, along with short, rapid tasks and quick pivots after failures. Unit 42 reads those as strong signs of an agentic attacker. For defenders that's also a hunting lead: those labelled delimiters in command output on a PHP host are not something a human operator typically bothers with.

Elsewhere on the same flaws, Defused Cyber reports probes against its honeypots that imitate Palo Alto GlobalProtect devices, carrying a marker that suggests someone is building a target list of those appliances. Bitsight counts nearly thirty-seven million internet-facing systems running PHP or related software. And ReliaQuest has published a detection pattern from its lab: a POST request returning a server error, PHP logging memory exhaustion and heap corruption, then the Apache worker crashing. The fixed versions remain PHP eight point five point twelve, eight point four point twenty-seven, eight point three point thirty-six and eight point two point thirty-five, and the flaws are still not in CISA's known exploited catalogue, though after this week that looks more a question of when than if. Details and the detection notes are in the show notes.

Next, Tailscale. A researcher, Erica Windisch of Cyberdione Labs, has published a report called Tailworm, with eleven findings in Tailscale and in headscale, the self-hosted control server some organisations run instead. The headline finding: where Tailscale SSH allows port forwarding, an attacker who already controls one approved device can reach root on other servers that device is permitted to connect to. In the lab, the chain went further, capturing a key used to enrol new devices and joining the attacker's own machine to the network, though that last step only completed where Tailnet Lock was switched off. Other findings cover an experimental app connector feature that can reach destinations the security team never approved, including cloud metadata services that hand out credentials, and resource exhaustion in headscale. To be clear about scope, this is lateral movement from a foothold, not a way in from the internet, and the findings have not yet been reproduced by anyone else. There is no bulletin, no CVE number, and no fix yet. Tailscale's vice president of engineering says the company has found issues it is working to fix, but is not recommending that everyone disable Tailscale SSH. In the meantime, write SSH rules as single device-to-target pairs, which the report says stopped the spread in testing, turn off SSH forwarding where you can, strip app connector permissions from devices that don't need them, and turn on node-key expiry. On headscale, forwarding can't be switched off at all, so treat every SSH grant there as root on the target.

AI security.

Researchers at Forever Security, which monitors risks from AI agents, found a coding agent on a customer's machine trying to install a malicious npm package. They traced it to a file called AGENTS dot md, sitting in the customer's Downloads folder, which also happened to be the folder the agent was started in. Coding agents automatically read instruction files like that from their working directory and follow them. The researchers point out that Downloads is the one folder a web page can write to on its own, since Chrome, Edge and Firefox save downloads there by default. They reproduced the attack against OpenAI's Codex with a harmless payload, succeeding about nine times in ten, and used a similar file against Anthropic's Claude Code to redirect its traffic and expose its login token. Those success rates are the researchers' own figures. They also say hundreds of their customers run coding agents from Downloads. As the researchers put it, there's nothing for the vendors to patch, because the agent is doing exactly what it was built to do. Which is, in its way, the most honest bug report of the week. The fix is behavioural: start agents only in the project folder you want them working on, read unfamiliar instruction files before letting an agent follow them, and keep approval prompts and sandboxing turned on.

And OpenAI has published a frank account of securing the environments it uses to train its most capable models. After an incident on the twentieth of September, when a research model exploited a misconfigured DNS resolver to gain limited access to the live internet, OpenAI paused frontier training for eleven days and set teams of its own agents to attack the containment. Those red-team agents worked on isolated copies of the infrastructure and were handed source code and notes on likely weaknesses, so these escapes were found under conditions deliberately tilted in the attacker's favour. They found ways to escape lightweight virtual machines, routes out to the internet through internal metrics, logging and authentication services, and covert ways to talk between sandboxes that were meant to be isolated, including one that used the processor's cache timing to pass secrets. OpenAI says it fixed these, contributed patches to open-source projects such as Kata Containers and gVisor, resumed training on the first of October, and now trains frontier models with no live internet access at all. This is OpenAI describing its own systems, so the detail is self-reported. For anyone running agents with code execution, the lesson travels well: the sandbox is one layer, and the network and cloud controls around it need to hold even when the sandbox doesn't.
